## 書くときの決まり（誤りを出さないため。2026-10-28 に足したもの）
- 文の中身は、その資料のその箇所の原文で確かめられることだけにします。数字・日付・名称・条番号・問番号は、python で原文の文字列を探して確かめます（全角は半角にそろえ、空白を除いて探す）。資料は `scripts/fetchtext.py` で文字にしたものを読みます。
- 日付は役割を区別して書きます（公布日・施行日・公表日・開催日・申請や届出の期限・対象期間）。要綱や告示の「◯日から施行」を、事業や制度が始まる日と取り違えません（実例：福岡県の補助金の要綱の施行日 8月24日を「8月から実施」と書き、対象期間 4/1〜2/28 と申請期限 10/13 を落としていた）。
- 期限のあるもの（申請・届出・申込・意見募集）は期限も書きます。今日より前の期限を、これからのことのように書きません。
- milestones（ホームの「近づいている期限」）の title は、その日付が何の日か（申込の期限・開催日・送付日・受信確認の期限など）を資料の言葉どおりに書きます。資料に期限と書かれていない日を「〜の申込」「〜まで」のように期限として書きません（実例：全国説明会の視聴URLが届く日 11月4日を「申込」の日として載せていた）。同じ催しを events にも載せるときは、milestones の日付と events の日付の役割が読んで分かるようにします。
- 本文の根拠の表記（Q&A の src、章の「ref」）は、資料リンク集の台帳 `dbs/_src/links.json` にある資料の呼び名（cite）で書きます。新しい資料を根拠にするときは、links.json にその資料を {g, t, u, d, cite} で足します。`build.py` は、根拠の表記がどの資料にも結びつかないと止まります。

## 手順

### 1. リポジトリを用意する
mcp__claude-code-remote__add_repo を owner "kanda-houtokukai"、repo "fukushi-watch"、access "push" で呼び、返ってきた案内どおりに `git clone --depth 1` します（時間に余裕をもたせる）。push の権限が得られなかったときは、書き換えずに止め、理由を最後の報告に書きます。

### 2. 更新データを読む
`dbs/_src/live.json` を python で読みます。構成は checkedAt・checkedPages・checkNote・notices・milestones・updates・eventsFocus・eventsLocalNote・events・library・watch です。

### 3. 確認する
live.json の watch に並ぶページを `scripts/fetchtext.py` で読んで確認します（url が空の行は WebSearch で探し、見つけたURLを読みます）。ほかに WebSearch で次を調べ、気になる結果はそのURLを `scripts/fetchtext.py` で読んで確かめます。
- 「こども性暴力防止法」「日本版DBS」の新しい通知・資料・Q&A改訂・ガイドライン改訂・システム（こまもろう）・マニュアル・ヘルプデスクの発表
- 福岡県・福岡市・北九州市・久留米市・県内の業界団体（社会福祉協議会、保育協会、知的障がい者福祉協会など）が開く説明会・研修
- 全国からオンライン（Zoom・YouTube・オンデマンド）で参加できる、事業者向けのセミナー・研修（主催企業・社労士・弁護士・業界団体・告知サイト）
前回の最終確認（checkedAt）より後に出たもの、内容や状態が変わったもの（締切、満席・キャンセル待ち、中止、アーカイブの公開、日付の確定）を拾います。すでに updates や events にあるもの（同じURL・同じ件名）は足しません。

### 4. 更新データを書き換える
JSON の形を保ったまま、次のとおり書き換えます。日付は日本時間の ISO 形式（例 2026-11-06、時刻つきは 2026-11-06T14:00:00+09:00）。
- checkedAt: 今の日時（見積もらずに `TZ=Asia/Tokyo date +%Y-%m-%dT%H:%M:00+09:00` で取る）。checkedPages: 今日開いて確かめたページの数。checkNote: 今日の確認の結果を1文で（例「こども家庭庁がQ&Aを改訂しました」「新しい発表はありませんでした」）。
- updates（新しい発表）: 先頭に足します。項目は {date: 発表日, src: "国"|"自治体"|"研修"|"その他", title, url, impact, note, where}。impact は、ガイドの本文の書き換えが要るなら、手順5で反映できたものは "done"、反映できなかったものは "todo"、本文に影響しない参考情報なら "info"、更新データの書き換え（研修の追加など）だけで対応が済んだなら "done"。where はガイドの関係する章の #id（#now #checklist #schedule #tools #overview #scope #persons #check #timing #system #safety #inappropriate #incident #employment #info #docs #supervision #sectors #qa #events #updates #open #sources）。note は何が変わったかを1〜2文で具体的に。60件を超えたら古いものから消します。
- events（研修・説明会）: 新しいものは既存と同じ項目（id は英小文字とハイフンで一意に、start, end, date, fmt: ["online"|"venue"|"ondemand"|"fukuoka"], kind: "official"|"municipal"|"private", title, org, place, target, fee, cap, how, url, note, status, featured）で足します。福岡県内の会場なら fmt に "fukuoka" を入れます。民間の営業を含むものは note に書きます。満席は status "waitlist"、中止は "cancelled"、公開日が決まっていないものは "planned"。終了から60日を過ぎたものは消します。
- library（いつでも見られる動画・資料）: アーカイブや資料が公開されたら足します（kind, title, note, url）。
- milestones（ガイドのホームの「近づいている期限」）: 国が日付を確定・変更したら直します。たとえばシステムの暫定稼働日が発表されたら、その項目の date を確定日にし、approx と label を消します。
- notices（ガイドの全ページの上に出るお知らせ）: 2週間以内に法人が動く必要がある急な変更だけを {title, body, until, link} で足します。until を過ぎたものは消します。
- eventsFocus と eventsLocalNote: 福岡からの参加に関する案内を、事実に合わせて直します（until を過ぎた eventsFocus は消すか更新）。
- watch: 新しく確認すべきページ（例：福岡県障がい福祉課の専用ページ）が見つかったら足します。
書き出しは `json.dumps(data, ensure_ascii=False, indent=1)` に改行を1つ足した形にします。
新しい資料（通知・Q&A の改訂など）は、`dbs/_src/links.json` にも {g, t, u, d, cite} で足します（資料リンク集に載る）。すでに引いている資料の新しい版が出たときは、`python3 scripts/audit.py dbs --due-source <古い版のURL>` を実行します（その資料を引く本文が、次の見直しで先に回る）。

### 5. 本文を直す（新しい発表で本文の事実が古くなったとき）
1. 直す箇所ごとに、今の文・直した文・根拠（資料のURL・箇所・原文の引用）を作業用のファイルに書き出します。直すのは事実の部分だけで、言い回しと構成は変えません。
2. **別の担当に照合させます。** Agent ツール（subagent_type "general-purpose"）を1つ起動し、渡すのは「その作業用のファイルのパス」「資料を文字にしたファイルのパス」「本文のファイルのパス」と、次の基準だけにします（自分の考えや下書きの経緯は渡さない）。照合する担当への指示には「WebFetch は使わない。渡したファイルで足りない資料は `python3 scripts/fetchtext.py URL` で読む」も入れます。基準：直した文の事実の1つずつが、資料の原文で裏づけられるかを確かめ、直しごとに「合格／不合格」と理由・原文の引用を返す。原文で確かめられない事実を含む直し、日付の役割の取り違え、過ぎた期限をこれからのことのように書いている直しは不合格。
   Agent ツールが使えないときは、自分で別の回として照合します：資料の文字を開き直し、直した文ごとに裏づける原文を書き出し、書き出せない直しは不合格にします。
3. 合格した直しだけを本文に当て、直した単位ごとに `python3 scripts/audit.py dbs --mark <単位> fixed --note "MM/DD ◯◯の改訂で直した"` を実行します（単位の名前は `python3 scripts/audit.py dbs --next 200` の unit で分かる）。不合格の直しは当てず、updates に impact "todo" で記録します。

### 6. 毎朝の見直し（すでに載っている本文の照合）
1. `python3 scripts/audit.py dbs --next 4` で、照合がいちばん古い4つの単位（章・Q&Aの1問・判定ツール・チェックリスト・期限の一覧）を、本文と根拠の資料つきで出します。
2. それぞれ、根拠の資料の該当箇所を開き、事実を1つずつ原文と照らします（日付の役割と、今日より前になった期限にも気をつける）。
3. 食い違いがなければ `python3 scripts/audit.py dbs --mark <単位> ok` を実行します。
4. 食い違いがあれば、手順5と同じやり方（事実だけを最小限に直す→別の担当の照合→合格したものだけ当てる）で直し、`--mark <単位> fixed --note "何を直したか"` を実行します。

### 7. 組み立てて push する
1. `python3 dbs/_src/build.py` を実行します（dbs/index.html が組み立て直されます）。止まったときは表示に直し方が出るので、それに従って直し、組み立て直します（例：画面の文に「まだ」「いま〇〇」があれば事実の言い方に直す。根拠の表記が資料に結びつかなければ links.json の cite を足すか表記を直す）。直せないときは push せず、理由を報告します。
2. `git status --short` で、変わったのが `dbs/_src/live.json`・`dbs/index.html`・`dbs/_src/audit.json`・`dbs/_src/links.json`・`dbs/_src/sections/`・`dbs/_src/data.js` の中だけであることを確かめます。ほかのファイルが変わっていたら push せずに止めます。
3. commit します。メッセージは「ガイド: 毎朝の更新 MM/DD（新しい発表◯件・研修◯件・本文の直し◯件・照合◯件）」。
4. `git fetch origin main` → `git rebase origin/main` → `git push origin HEAD:main`。`dbs/index.html` でぶつかったら、そのファイルを origin/main の版にしてから `python3 dbs/_src/build.py` を走らせ直し、`git add dbs/index.html` して `git rebase --continue` します（組み立ての出力なので、手で混ぜない）。拒否されたら同じ手順をもう1回だけ行い、それでも駄目なら止めて報告します。変化がなかった日も、最終確認の日時を更新するために push します。
5. 公開URLの HTML に今日の checkedAt が入るまで、最長10分ほど確かめます（GitHub Pages の反映待ち）。

### 8. 最後の報告（通知に使われます）
最終メッセージは3行以内にします。
- 1行目：新しい発表◯件、研修・説明会の追加◯件、本文の直し◯件、照合◯件（食い違い◯件）、本文の書き換え候補◯件
- 2行目：いちばん重要な1件の要約。本文を直したときは「取り消すときは、この会話に『取り消して』と返信してください」と添える。本文の書き換え候補があれば「どの章の何を、どの資料にもとづいて直すか」を短く書く
- 3行目：https://fukushi-watch.fknd.jp/dbs/#updates

新しい発表も研修の追加もなく、照合でも食い違いがなかった日は「変化なし（最終確認 MM/DD HH:MM・照合◯件）」の1行だけにし、通知は要りません。タスクが失敗した日は、失敗した手順と理由を書きます。

## 文体のルール
- 日本語で、平易かつ具体的に書く。公式資料の用語（施行時現職者、犯罪事実確認、いとま特例など）はそのまま使う
- AIっぽい体言止めの二句コピー（「○○、○○。」型）や、物語調の語り口は使わない
- 画面に出る文に「まだ」は使わない（「未公表」「公表待ち」など事実で書く）
- 画面に出る文に「いま〇〇」（いまの段階・いまここ・いますぐ など）や「今すぐ」を使わない（「◯月◯日時点」など事実で書く）。`build.py` は「まだ」とこれらを含むと止まる
- 画面に出る文に、サイトの仕組みの説明（「毎朝確認しています」など）・操作の説明・作り手の語り（「〜をまとめました」など）を書かない
